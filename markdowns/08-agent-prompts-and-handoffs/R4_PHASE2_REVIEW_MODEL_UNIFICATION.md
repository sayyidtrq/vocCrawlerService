## The two models today (`app/db/models.py`)

`Review` (`reviews`) and `CompetitorReview` (`competitor_reviews`) share ~22
identical review-content columns (`reviewer_*`, `rating`, `review_text`,
`review_time`, `review_relative_time`, `*_language`, `like_count`,
`owner_response_*`, `scraped_at`, `raw_payload`, `review_hash`, `source`,
`external_place_id`, `external_review_id`, `created_at`, `updated_at`).

They differ in exactly these ways:

| aspect | `Review` | `CompetitorReview` |
| --- | --- | --- |
| tenant/parent FK | `company_id` -> companies, `location_id` -> locations | `competitor_id` -> competitors (no `company_id`) |
| analysis | `analysis_status` col + `analyses` relationship + `ReviewAnalysis` rows | none — competitor reviews are never AI-analysed |
| OneBox sync | `sync_updated_at` watermark col + `idx_reviews_company_sync_id` | none |
| extra indexes | `idx_reviews_source_place`, `idx_reviews_review_time`, `idx_reviews_rating` | `idx_comp_reviews_review_time` only |
| `review_hash` | `unique=True` | `unique=True` (separate table, so no cross-table guarantee) |
| dedupe identity | hash OR (`source` + `external_review_id` + (`external_place_id` else `location_id`)), company-scoped | hash OR (`competitor_id` + `source` + `external_review_id`) |

The dedupe divergence is a real latent bug the plan calls out: competitor dedupe
does not consider `external_place_id` and cannot be company-scoped. Reconcile it
whichever route you take.

Why they were split (from `CompetitorReviewService` docstring): only `reviews`
flows into the OneBox ticket pipeline; competitor reviews are comparison-only and
must never leak into tickets. Both have their own integration read endpoint
(`routers/integration_reviews.py`, `routers/integration_competitor_reviews.py`).

## Decision to make FIRST

Pick one and write a one-paragraph ADR-style note into
`markdowns/decisions/` (or append to the refactor plan) before coding.

### Option A — shared column mixin, keep two tables (RECOMMENDED, low risk)

Define a `ReviewColumnsMixin` (declarative mixin) carrying the ~22 shared columns.
`Review` and `CompetitorReview` each subclass it and add only their distinct
columns / FKs / indexes / relationships. No migration, no data movement, no
production risk. Kills the copy-paste, which is the actual maintenance cost.

Also: extract `CompetitorReviewRepository` mirroring `ReviewRepository`, and
collapse the two `_dedupe_statement` implementations into one shared helper
parametrised by (model, identity-columns, optional company scope) so the identity
logic can't drift again.

Cost: ~half a day. Benefit: 90% of the value at ~5% of the risk.

### Option B — single `reviews` table with a discriminator

One table, `kind` column (`'hospital'` / `'competitor'`), nullable `location_id`
AND `competitor_id` (exactly one set), nullable `company_id` (null for
competitor rows), nullable `analysis_status` / `sync_updated_at`. `CompetitorReview`
becomes a view or a `with_polymorphic` mapping.

This needs an Alembic migration that:
1. adds the nullable columns + `kind` to `reviews`,
2. copies every `competitor_reviews` row into `reviews` (watch `review_hash`
   uniqueness — hospital and competitor hashes are generated by the same
   `app/utils/hashing.py` helpers over different identity fields; audit for
   collisions before trusting a global unique index, or scope uniqueness by
   `kind`),
3. repoints or drops `competitor_reviews` and its FK,
4. has a real `downgrade()`.

Test it against a **local Postgres** (not just SQLite) — `docker-compose.postgres.yml`
is in the repo and `tests/test_postgres_concurrency.py` shows the fixture
pattern. Run `alembic upgrade head` then `alembic downgrade -1` then `upgrade`
again on a seeded DB.

Cost: 2-4 days with review. Risk: touches every review read/write path and a
live Supabase-Postgres schema. The team has had three deploy incidents from
smaller changes — treat this as its own release with a rollback plan.

**Recommendation: do Option A now.** Only do B if a concrete need appears
(e.g. cross-source dedupe, or a unified integration feed OneBox actually asks
for). The `CrawlTarget` work already removed the day-to-day pain of the split at
the service layer.
